Finite volume CFD in OpenFOAM - quick introduction

This is a short introduction to the finite volume method used in OpenFOAM. It does not serve as a comprehensive guide to CFD or OpenFOAM, but rather a quick overview of the main concepts. Please refer to the books suggested at the end of the page. There are five sections each dedicated to one the main concepts in Computational Fluid Dynamics.

Terms with a dotted underline open a short explanation. Boxes marked In OpenFOAM show where the idea lives in a case, and the links at the end of each chapter lead to the documentation and to books for the details this page skips.

All examples here are simplified java script computation to describe the basic idea. No OpenFOAM or any other CFD tool is involved.

The whole picture

A finite volume solver turns a set of partial differential equations into numbers representing the flow in four steps. Chapters 1 to 4 cover one step each, and chapter 5 shows where each choice is made in an OpenFOAM case.

  1. 1 · EquationsWhat do we solve?
    Which conservation laws are solved and what each term means physically. In the solver source every term is an operator such as fvm::ddt, fvm::div, fvm::laplacian or fvc::grad.
  2. 2 · Finite volumesWhat is a finite volume?
    The mesh is split into cells. Integrating an equation over one cell turns derivatives into sums of fluxes through the cell faces.
  3. 3 · SchemesHow are face values obtained?
    Fluxes need values on faces, but we only store values in cell centres. A scheme is the rule that interpolates between them.
  4. 4 · SolversHow is the system solved?
    One equation per cell gives a large sparse linear system A x = b, which an iterative linear solver solves approximately.
  5. 5 · Case setupWhere do I set it?
    Which file and keyword controls which of the steps above.

Equations to solve

Nearly every equation in a CFD solver is a variant of one template: the rate of change of a quantity φ equals what is carried in by the flow, plus what diffuses, plus what is created.

Momentum and continuity (incompressible)

Setting φ = U, Γ = νeff and adding the pressure gradient as the source gives the momentum equation. With kinematic pressure p (divided by density), as OpenFOAM does it:

∂U/∂t + ∇·(UU) − ∇·(νeff∇U) = −∇p
∇·U = 0νeff = ν + νt when a turbulence model is active. The extra transpose term of the stress is handled explicitly and omitted here.

The unknowns are U and p, but there is no evolution equation for p. Continuity is a constraint, and the pressure adjusts so that the velocity field stays divergence-free. Solvers such as simpleFoam and pimpleFoam combine the two into a , which is a Poisson problem and usually the most expensive linear system of the run.

Momentum equation, schematically

tmp<fvVectorMatrix> tUEqn
(
    ::ddt(U)                 // ∂U/∂t     implicit
  + ::div(phi, U)            // ∇·(UU)     implicit, phi = face flux
  - ::laplacian(nuEff, U)     // ∇·(ν∇U)    implicit
 ==
  - ::grad(p)                 // −∇p        explicit, from the latest p
);

fvm terms go into the matrix and are solved for; fvc terms are evaluated from known values and end up on the right-hand side. Chapter 4 shows what that means for the matrix.

The same equation in real solver source (simpleFoam, UEqn.H, abridged)

tmp<fvVectorMatrix> tUEqn
(
    fvm::div(phi, U)                 // ∇·(UU)   convection, implicit; phi is the face flux
  + MRF.DDt(U)                       // rotating-frame terms (zero without MRF)
  + turbulence->divDevReff(U)       // −∇·(ν_eff ∇U) and the transposed-gradient part, implicit/explicit split inside
 ==
    fvOptions(U)                     // optional user-defined sources
);
fvVectorMatrix& UEqn = tUEqn.ref();

UEqn.relax();                        // under-relaxation, factor from fvSolution
fvOptions.constrain(UEqn);

if (simple.momentumPredictor())
{
    solve(UEqn == -fvc::grad(p));    // pressure gradient from the latest p, explicit
    fvOptions.correct(U);
}

Differences from the schematic: simpleFoam is steady, so there is no ddt term. The viscous term is hidden inside the turbulence model (divDevReff), so laminar and turbulent runs share the same line. solve(…) assembles the matrix and hands it to the linear solver of chapter 4. Source details change between versions; check UEqn.H in your installation under $FOAM_SOLVERS/incompressible/simpleFoam.

The finite volume idea

Split the domain into small cells. For one cell of volume V, integrate the transport equation over it and apply the to turn volume integrals of divergences into sums over the cell faces:

∫V ∇·J dV = ∮∂V J·dS ≈ Σf Jf·SfJ is the flux vector: U φ for convection or Γ∇φ for diffusion. Sf is the face area vector pointing out of the cell.

Three consequences are worth keeping in mind:

  • Conservation is built in. What leaves one cell through a face enters its neighbour through the same face with the same value, so nothing is created or lost between cells.
  • Unknowns are cell averages stored at the cell centre ( arrangement). Everything else (face values, gradients) is reconstructed from them.
  • The face flux Ff = Sf·Uf (called phi in OpenFOAM, volumetric in m³/s for incompressible flow) is a single number per face. Do not confuse it with the transported quantity φ. Continuity says that for every cell Σf Ff = 0.

How well do cells represent a field?

A duct with a smooth area change, A(x) = 0.75 + 0.25 cos 2πx, carries steady incompressible flow with Q = 1 m³/s. Velocity u = Q/A and the Bernoulli pressure follow from the area, so we know the exact fields. The figure shows what cell averages make of them. It is a representation test, not a solver run.

How to read the errors

  • Cell value: what the method stores, the volume average of the exact field over the cell.
  • Error: cell value minus the exact value at the cell centre, in the units of the plotted field. It is not a solver error. Even a perfect average differs from the centre value wherever the field curves. The difference is second order in Δx (about Δx² f″/24 for a constant cross-section; here the average is also weighted by the duct area).
  • Interior vs end cells: end cells use the boundary face value instead of an average of two neighbours, so they converge more slowly in dp/dx.
  • Ratio to previous: error on the coarser mesh (half the cells) divided by error on this mesh. A ratio near 4 means error ∝ Δx², second-order. Near 2 means first-order. Near 1 means the mesh is still too coarse to see the trend.
  • max |ΣF|: the largest net face-flux imbalance of any cell, in m³/s. Continuity demands zero. With exact fluxes it is zero to round-off; with fluxes interpolated from cell values it is small but non-zero and shrinks as Δx². In OpenFOAM the flux phi is therefore not just the interpolated velocity: it is a separate field that the pressure equation makes conservative, while the interpolated cell velocities satisfy continuity only to this accuracy.

A real solver does not rely on interpolated velocities for conservation: the pressure equation delivers conservative face fluxes directly.

Plane Poiseuille flow between two walls (gap H = 20 mm, mean velocity 0.15 m/s) has a parabolic profile. The cells now stack across the flow, which is how a boundary layer is resolved. Cell values are exact averages of the parabola.

Wall shear gradient du/dy

Inside the domain, the central difference of two neighbouring cell averages hits the exact gradient of a parabola at the shared face. At the wall there is no neighbour: the gradient is taken as uP/(Δy/2), which is only first-order accurate. That is why wall-resolving meshes need thin first cells, and why this error drives the wall-shear and heat-transfer accuracy.

In OpenFOAM

Mesh: constant/polyMesh stores faces with their owner and neighbour cells, from which V and Sf follow.

Face flux: phi is a surfaceScalarField (one value per face) that the solver computes from U.

Face sum: the choice of how the sum is formed is made in system/fvSchemes by the keyword Gauss, e.g. gradSchemes { default Gauss linear; }. The interpolation named after it is the topic of the next chapter.

Spatial discretisation: choosing the face value

The convective flux through a face needs φf, but we only store cell centres. How we guess the face value is the . Three are enough to see the trade-off.

  • : take the value from the upstream cell. First-order accurate, always bounded, but smears gradients.
  • (central differencing): average of the two cells. Second-order accurate, but can produce oscillations.
  • : upwind value plus a gradient-based correction. Second-order, usually a good default for steady RANS.

How the face value is formed between neighbouring cells

Flow goes from left to right through the face f between cell P (upstream of the face) and cell E. Cell W lies further upstream and matters only for linearUpwind. The solid ring on the dashed face line is the face value φf that enters the flux Ff φf.

The test case is the steady 1D convection–diffusion equation u φ′ = Γ φ″ on 0 ≤ x ≤ 1 with φ(0)=0, φ(1)=1. The exact solution is flat and then rises sharply at the outlet when convection dominates, a thin boundary layer, which is a harsh test for any scheme. The control parameter is the Pe = uL/Γ.

Algebraic solvers

4.1 Where the matrix comes from

Write the discretised equation for cell P: its unknown multiplied by a coefficient, plus each neighbour's unknown times a coefficient, equals a known right-hand side.

aP φP + ΣN aN φN = bPOne such row per cell stacks into A φ = b. A is square, sparse (only face neighbours are non-zero) and has one row per cell.

In a 1D line of cells numbered left to right, cell P has a west neighbour W and an east neighbour E, and the sum has just two terms:

The coefficient of the cell itself, aP, sits on the matrix diagonal. The west neighbour has a lower index, so aW is left of the diagonal (lower triangle); aE is right of it (upper triangle). Colours match the matrix below. The coefficients collect what the two faces w and e contribute: face flux and diffusion across each.

The diagonal aP collects contributions from all faces of the cell, the off-diagonals aN one per neighbour. Pick a discretisation below and click a row to see how it is assembled.

Diffusion alone gives a symmetric matrix with a positive diagonal and negative off-diagonals. (This is the sign of −∇·(Γ∇φ), the way the term enters the equation; fvm::laplacian on its own has the opposite signs.) Convection breaks the symmetry. A positive off-diagonal (red) is the algebraic signature of the unbounded behaviour from chapter 3. For linearUpwind the matrix shown is the upwind one; the gradient correction sits in the right-hand side.

In OpenFOAM

The matrix is stored in LDU format, not as a table: diag() (one value per cell), upper() and lower() (one value per internal face), addressed through owner and neighbour. A symmetric matrix stores only upper. The symmetry matters for the choice in fvSolution: PCG works only for symmetric matrices (pressure), PBiCG is its counterpart for asymmetric ones, and PBiCGStab, smoothSolver and GAMG handle both.

4.2 Solving it: three basic ideas

  • (Gauss–Seidel): sweep through cells and update each from its neighbours' latest values. Cheap per sweep, removes local (high-frequency) error fast, but long-wave error decays very slowly on fine meshes.
  • (conjugate gradient, with a preconditioner such as DIC): for symmetric matrices. Each iteration picks a search direction that does not undo earlier progress. Iterations grow roughly with the mesh size in one direction.
  • (geometric-algebraic multigrid): smooth on the fine mesh, correct the smooth remaining error on a coarser mesh where it looks short-wave, and repeat down to a few cells. Iteration count stays nearly independent of mesh size.

The demo solves the 2D Poisson equation −∇²φ = 1 with φ = 0 on all walls, the same structure as the pressure equation. Pick a solver and mesh size, then step through or run to convergence.
